# LLM voice bench — 2026-09-30

One realistic witness-voice call (Petunia Wicks, `confirms`, real fact) ×3 per model,
8 s cooling gaps, one 429-retry. `scripts/llm-bench.ts`.

## Result: free shared pools were saturated — every call fell back to stub

| model | n | median ms* | live% | failure modes observed |
|---|---|---|---|---|
| poolside/laguna-xs-2.1:free | 3 | 8523 | 0 | 429 upstream rate-limit |
| liquid/lfm-2.5-2.6b:free | 3 | 9389 | 0 | 429 upstream rate-limit |
| nvidia/nemotron-3.5-lightning:free | 3 | 28948 | 0 | 429, empty content, non-JSON |
| google/gemma-4-26b-a4b-it:free | 3 | 142 | 0 | (not reached — see below) |

\* Median measures stub-fallback latency, not the model. Do not quote it as model speed.

Direct probes confirmed the cause: OpenRouter returns instant `429
"temporarily rate-limited upstream ... upstream_provider_shared_pool"` across
laguna, gemma, and liquid pools alike. Request shape is correct (proper
provider error, not a client 4xx). Nothing to conclude about per-model speed
or JSON discipline from this run.

## Design consequences (implemented)

1. **Cascade, not single model.** `LLM_VOICE_MODEL` accepts a comma-separated
   list; `DirectLLMClient` falls through 429/5xx/network failures to the next
   model inside the same 6 s voice budget, then stub. Default:
   `laguna-xs → gemma-4-26b → lfm-2.5`. A saturated pool costs one fast 429
   (~0.4 s), not the trial.
2. **Single-model bench retained** for off-peak re-runs: `npx tsx scripts/llm-bench.ts <model>`.
3. Earlier CLI-harness timings (for the record): `opencode run` floor ≈ 6–9 s
   regardless of model (`--attach` to a persistent server measured identical),
   `--variant minimal` saved ~1.5 s. The direct HTTP path removes the harness
   entirely; per-call latency is now model + network only.
